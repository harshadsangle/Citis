Implement **CITIS LMS Step 7 — Certificate Lifecycle, Admin Approval & Reporting**.

Use completed Steps 1–6 as the source of truth.

### 1. Certificate Eligibility

A student becomes **eligible for certificate review** only when all required course completion conditions are satisfied:

* Required lessons completed
* Required assessments passed
* Required assignments completed
* Required assignments passed
* Overall course completion verified server-side

Do NOT issue a certificate automatically.

Create a clear certificate status lifecycle such as:

* `NOT_ELIGIBLE`
* `ELIGIBLE_FOR_REVIEW`
* `APPROVED`
* `REJECTED`
* `ISSUED`
* `REVOKED`

Use the existing certificate architecture where possible.

### 2. Admin Approval

Only `CITIS_ADMIN` can approve/reject certificates.

Admin must be able to:

* View certificate-eligible students
* Review course completion
* Review assessment results
* Review assignment results
* Approve certificate
* Reject certificate
* Add approval/rejection notes
* Record reviewer and timestamp

Instructor must NOT approve, reject, issue, revoke, or modify certificates.

Student must NOT approve or generate their own certificate.

### 3. Certificate Generation

After Admin approval:

* Generate the certificate using the existing certificate system.
* Certificate must reference:

  * Student
  * Course
  * Completion date
  * Certificate ID
  * Issued date
* Certificate ID must be unique.
* Do not generate duplicate certificates for the same approved completion unless explicitly required.
* Preserve certificate history.

If a PDF certificate is generated, store it using the existing secure file/storage architecture.

Do not expose private storage credentials.

### 4. Certificate Verification

Implement a public certificate verification mechanism.

A person with a valid Certificate ID should be able to verify:

* Certificate is valid/invalid
* Student name as appropriate
* Course name
* Issue date
* Certificate status

Do NOT expose:

* Student login credentials
* Email
* Phone number
* Private activity
* Payment information
* Assignment files
* Assessment answers
* Other private data

Revoked certificates must show the correct revoked status.

### 5. Certificate APIs

Add/extend APIs for:

* Certificate eligibility
* Admin certificate review
* Certificate approval
* Certificate rejection
* Certificate issuance
* Certificate lookup
* Certificate verification
* Certificate revocation where required

Enforce role-based authorization on every endpoint.

### 6. Student Certificate Access

Students should be able to see their own certificate status:

* Not eligible
* Eligible for review
* Under review where supported
* Approved
* Issued
* Rejected
* Revoked

Students can access/download their own issued certificates where supported.

A student must never access another student's certificate.

### 7. Reporting System

Implement Admin reporting using the existing database and activity structures.

Only `CITIS_ADMIN` can access global reports.

Reports should support filters where appropriate, including:

* Date range
* College/institution
* Student type
* Student
* Course
* Instructor
* Completion status
* Assignment status
* Assessment status
* Certificate status
* Payment status

### 9. CSV Export

Admin must be able to export filtered report data as CSV.

Requirements:

* Export only filtered/authorized records.
* Correct CSV headers.
* Safe CSV escaping.
* Consistent date/time formatting.
* Do not export passwords, OTPs, secrets, or sensitive authentication data.
* Do not expose unnecessary private information.

Large exports should be handled safely according to the existing architecture.

### 10. Multi-Tenant Security

Strictly enforce existing access rules.

`CITIS_ADMIN`:

* Global access.

`INSTRUCTOR`:

* No global reporting access.
* Only authorized assigned-college/student information where the existing instructor permissions allow it.

`STUDENT`:

* Only their own certificate/status information.
* No global reports.

College A data must never appear in College B scoped results.

### 11. Audit Trail

Record important certificate actions:

* Eligibility calculated
* Admin review started
* Certificate approved
* Certificate rejected
* Certificate issued
* Certificate revoked

Record:

* Actor
* Timestamp
* Student
* Course
* Certificate
* Action

Do not store unnecessary sensitive data.

Certificates and reports must reference the existing course/enrollment/assessment/assignment records.

Do not modify existing course content.

### 14. Security

Verify:

* Only Admin can approve certificates.
* Only Admin can revoke certificates.
* Certificate IDs cannot be guessed to expose private data.
* Student certificate access is ownership-checked.
* Reports are authorization-protected.
* CSV exports cannot leak sensitive information.
* Cross-tenant data access is blocked.
* Certificate eligibility cannot be manipulated from the client.
* Certificate issuance cannot be triggered by the client without Admin approval.
